01 / Project overview

One platform for the complete booking journey.

SeatSync centralizes event discovery, show scheduling, seat inventory, booking, cancellation and platform administration in one full-stack web application.

🎯

Project objective

Build a secure and reliable event booking experience with interactive seat selection, role-based access and consistent seat availability—even when multiple users try to book at the same time.

⚠️

Problem being addressed

Manual seat allocation, unclear availability, duplicate booking attempts, disconnected cancellation processes and limited visibility for event organizers.

Core technical challenge: prevent two customers from confirming the same seat for the same show. SeatSync addresses this with conditional atomic updates, temporary seat locks and MongoDB transactions.

users.email

Data modelling rule: a seat number such as A5 may exist in many different shows, but the combination of showId + seatNumber must be unique. Every show gets its own seat inventory.

Seat states

The final application will display seat status from the selected show. Customers can select only available seats. The backend must re-check availability when a hold request arrives; frontend state alone cannot prevent double booking.

  • Available: can be selected by a customer.
  • Selected: chosen in the current interface.
  • Locked: temporarily held for a user until the lock expires.
  • Booked: confirmed and unavailable to others.
07 / Core engineering challenge

Preventing double booking.

Two customers may request the same seat at almost the same time. The server—not the browser—must decide who gets the seat.

REQUEST A

Customer A requests A5

The server conditionally changes the seat from AVAILABLE to LOCKED, storing the customer and lock expiry.

REQUEST B

Customer B requests A5

The same conditional update no longer matches because the seat is already locked. The request is rejected as unavailable.

01Select seats
→
02Check availability
→
03Atomic seat lock
→
04Confirm booking
→
05Transaction commits
Implementation notes: use conditional atomic updates to acquire locks. Confirm multiple seats and create the booking inside a MongoDB transaction so all changes succeed or roll back together. Transactions require a replica-set-capable MongoDB deployment. Lock expiry needs explicit cleanup and ownership checks; a TTL index alone does not safely release seat status. Cancellation should transactionally cancel the booking and release only seats associated with that booking.
